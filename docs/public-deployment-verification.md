# Public deployment verification record

Use this checklist after deploying the frontend to GitHub Pages and the read-only API to the selected backend host.

## Deployment details

```text
Frontend URL: https://<github-user>.github.io/Global-Digital-Banking-Starter/
Backend URL: https://<your-backend-host>
Frontend commit:
Backend commit:
Deployment date:
Verifier:
```

## Public endpoint checks

- [ ] `GET <Backend URL>/api/health` returns HTTP `200`.
- [ ] The health response contains `status`, `service`, `version`, and `requestId`.
- [ ] `GET /api/knowledge` returns a collection response.
- [ ] `GET /api/resources` returns a collection response.
- [ ] `GET /api/membership/plans` returns a collection response.
- [ ] `GET /api/demo/profile` identifies the data as prototype-only.
- [ ] `GET /api/demo/accounts` returns fixture data only.
- [ ] `GET /api/demo/transfers` returns fixture data only.

## Frontend route checks

Test these routes from the public GitHub Pages site:

```text
/knowledge
/resources
/membership
/dashboard
```

For each route:

- [ ] Direct navigation loads successfully.
- [ ] Hard refresh loads successfully.
- [ ] Internal SPA navigation loads the correct page.
- [ ] Browser back navigation restores the correct page and data.
- [ ] Browser forward navigation restores the correct page and data.
- [ ] API loading status is visible while the request is pending.
- [ ] API success state removes the loading status.
- [ ] No duplicate API status banners appear.
- [ ] No stale response overwrites the current route.
- [ ] Empty collections show a usable empty state.

## CORS and browser checks

In browser developer tools:

- [ ] API requests complete without CORS errors.
- [ ] The response `Access-Control-Allow-Origin` matches the exact frontend origin.
- [ ] No secrets, credentials, session tokens, or private identifiers appear in page source or network requests.
- [ ] Values returned by the API are rendered safely.
- [ ] No unexpected third-party requests are present.

Expected browser API requests are read-only `GET` requests:

```text
GET /api/health
GET /api/knowledge
GET /api/resources
GET /api/membership/plans
GET /api/demo/profile
GET /api/demo/accounts
GET /api/demo/transfers
```

Confirm that no `POST`, `PUT`, `PATCH`, or `DELETE` request is generated by the frontend.

## Failure-mode checks

- [ ] Stop or disable the backend.
- [ ] Reload `/knowledge`, `/resources`, `/membership`, and `/dashboard`.
- [ ] Each route remains usable with its local preview or fallback content.
- [ ] A clear warning explains that the API is unavailable.
- [ ] No uncaught JavaScript error prevents navigation.
- [ ] Restart the backend and confirm API data loads again.

## Prototype safety checks

- [ ] Dashboard content is visibly labeled prototype-only.
- [ ] No real customer data is present.
- [ ] No real account balance is implied.
- [ ] No transfer can be created, approved, cancelled, or submitted.
- [ ] No payment provider is contacted.
- [ ] No database or ledger mutation is possible.
- [ ] Demo fixture identifiers cannot be mistaken for production identifiers.

## Deployment and operations checks

- [ ] GitHub Actions deployment completed successfully.
- [ ] The deployed commit SHA is recorded above.
- [ ] Backend health checks are passing.
- [ ] Backend logs are available to the operator.
- [ ] Request IDs are returned by the API.
- [ ] Secrets are stored in the hosting platform, not in Git.
- [ ] The backend binds to `0.0.0.0` in the hosted environment.
- [ ] `CORS_ORIGIN` is the exact deployed frontend origin.
- [ ] Rollback instructions are available.
- [ ] A separate staging environment is planned before production capability.

## Next gate

Proceed to identity and authorization implementation planning only if all checks pass or every failure has an owner and documented remediation plan.

The next design work is limited to:

1. identity provider selection;
2. user lifecycle and profile persistence;
3. session management;
4. authorization middleware;
5. audit event modeling;
6. security and privacy testing.

Do not add ledger posting, account mutations, transfers, payments, provider integrations, or real financial data at this gate.
